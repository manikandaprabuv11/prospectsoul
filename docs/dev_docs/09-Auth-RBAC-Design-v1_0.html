ProspectSoul · Technical Design Companion

Access control & authentication design

A role-based access control system built on Keycloak OIDC: one realm, two clients, five roles, enforced at the server and mirrored — never substituted — in the UI.

Version 1.0 Companion to Technical Design Spec v1.0 Status Draft for review

01 Principles

Five rules govern every decision in this document. Where an implementation choice isn't obvious, resolve it against these first.

  • Authorization is a backend concern. The UI hides buttons a role can't use, but the API is the actual gate. A hidden button and a missing @PreAuthorize are not the same control.
  • Roles are coarse by design. Five roles map to how the small internal team actually works today (PRD §2). Splitting roles further is a configuration change in Keycloak, not a code change.
  • Every mutation is attributable. The actor in every audit row comes from the validated JWT, never from a client-supplied field.
  • Tokens are ephemeral, sessions are not silently extended. Silent refresh keeps a logged-in analyst working; it does not paper over an expired or revoked session.
  • The identity provider owns identity. ProspectSoul never stores passwords, never implements its own login form, and never re-implements MFA. Keycloak is the source of truth for who someone is; ProspectSoul only asks what they're allowed to do.

02 Identity provider architecture

Keycloak is the single identity provider for ProspectSoul and every other Vyoog Spring Boot application. One realm, two OIDC clients, five realm roles.

RealmvyoogShared across Vyoog internal tools, not created per-product

Why bearer-only, not confidential The SPA can't keep a client secret safe in a browser, so prospectsoul-web is public and relies on PKCE. The API never accepts credentials directly — it only ever validates a token that Keycloak already issued.

It is part of the identity design but must not be built or wired up until a real programmatic source exists — see Developer Guide §14.

04 Authentication flow

The SPA never sees a password. It redirects to Keycloak, gets a code, exchanges it for tokens, and keeps the session alive with silent, invisible refreshes.

Frontend responsibilities

  • keycloak-js initializes on app load; unauthenticated users are redirected, not shown a local login form.
  • Access tokens live in memory (the keycloak-js adapter's internal state) — never in localStorage — so a stale tab reload always re-establishes the session cleanly.
  • Silent refresh runs in a hidden iframe ahead of token expiry. A failed refresh (session revoked, SSO expired) forces a real redirect to login, not a silent failure.
  • The API client wrapper attaches the current access token to every request; it does not attempt to refresh tokens itself — that's the adapter's job.

05 Request authorization flow

Every request is authorized twice by the time it reaches business logic: once by Spring Security's resource-server filter (is this token valid?), once by method security (is this role allowed to call this method?).

Backend implementation

@RestController
@RequestMapping("/api/v1/companies")
public class CompanyController {

    @PreAuthorize("hasAnyRole('PS_ANALYST','PS_SALES_LEAD','PS_ADMIN')")
    @PostMapping
    public CompanyDto create(@RequestBody @Valid CompanyCreateRequest req,
                             Authentication auth) {
        // actor id read from auth.getName() (JWT subject) — never from the request body
        return companyService.create(req, auth);
    }

    @PreAuthorize("hasAnyRole('PS_ANALYST','PS_SALES_LEAD','PS_ADMIN','PS_VIEWER','PS_COO')")
    @GetMapping
    public Page<CompanyDto> search(CompanySearchRequest q) { ... }
}
Invariant, restated from Developer Guide §16 Authorization is enforced server-side, per method, via @PreAuthorize. A frontend route guard is a UX convenience layered on top of this — it is never the control itself.

07 Frontend route & action guards

The UI mirrors §3 exactly, for usability — a Viewer should never see an Export button they'd get a 403 on. It is a convenience, not a boundary.

// auth/guards.ts
export const canMutateCompany = (roles: Role[]) =>
  roles.some(r => ['PS_ANALYST', 'PS_SALES_LEAD', 'PS_ADMIN'].includes(r));

export const canExport = (roles: Role[]) =>
  roles.some(r => ['PS_SALES_LEAD', 'PS_ADMIN'].includes(r));

export const canConfigure = (roles: Role[]) => roles.includes('PS_ADMIN');

// route definition
<Route path="/settings" element={
  <RequireRole allow={['PS_ADMIN']}><SettingsPage /></RequireRole>
} />
  • Sidebar navigation is role-filtered at render time (UI/UX Spec §1) — Settings never appears for non-Admins, Ready Pool/Exports never appear below Sales Lead.
  • Action buttons (Disqualify, Override, Export, Configure) check the same guard functions; a denied action is hidden, not disabled-with-tooltip, to keep the screen uncluttered — this is a product choice, revisit if users ask "why can't I see X."
  • Guards read roles from the decoded access token already held by the keycloak-js adapter; they do not make a network call to determine permissions.

08 Error handling

Authorization failures are ordinary application/problem+json responses — no special-cased error shape for auth.

StatusMeaningTypical cause
401UnauthenticatedMissing, expired, or malformed bearer token
403Role deniedValid token, role lacks the required authority for this method
 
{
  "type": "https://prospectsoul/errors/forbidden",
  "title": "Role denied",
  "status": 403,
  "detail": "PS_VIEWER cannot create companies"
}
UX rule, from UI/UX Spec §4 Errors surface the detail field verbatim — no generic "something went wrong," including for 401/403.

09 Audit trail integration

Authentication and authorization feed directly into auditability — the actor on every row is a validated identity, not a claim the client made.

  • Every mutating service method calls AuditService.record(entityType, entityId, actorId, action, previousState, newState) explicitly — never a listener triggered by magic (Developer Guide §7, §16).
  • actorId is always read from the validated JWT subject (auth.getName() / sub claim), inside the same transaction as the mutation.
  • Role-restriction tests (403 paths) are part of the Definition of Done for every sprint (Roadmap §0) — not an end-of-project hardening pass.

11 Testing requirements

Directly from Implementation Roadmap, Sprint 1 acceptance criteria and the standing Definition of Done.

  • Each of the five seed roles can log in against the local Keycloak realm.
  • Viewer receives 403 on POST /companies (and every other mutating endpoint) — tested, not assumed.
  • Every sprint that introduces a new mutating endpoint adds a corresponding 403 test for the roles excluded from it, per the matrix in §3.
  • Integration tests (Testcontainers) exercise real JWTs issued by a test Keycloak realm — not a mocked Authentication object standing in for the whole filter chain.
