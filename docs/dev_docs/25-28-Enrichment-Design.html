Six architectural amendments (prerequisites)

An architecture review identified six additions the platform needs before enrichment ports in. Not optional. Apply to all future enrichment work too.

  1. Enrichment is a first-class module. External calls don't live inside CompanyService or research/. They live in enrichment/<provider>/ behind a common SPI.
  2. Generalize research_queue → enrichment_jobs. Existing AI flow keeps working via a bridging shim; full migration is a Phase 1.5 follow-up.
  3. Facts / Evidence / Scores — three distinct concepts (see below).
  4. Evidence extends to any observation, not just AI claims. Additive columns, existing AI-evidence rows remain valid.
  5. Provider abstraction owns operational plumbing — rate limits, retries, timeouts, idempotency, cost, provenance. Providers write only the API call and result mapping.
  6. Enrichment contributes to the existing Company Timeline. No parallel history system.

Business invariants (extending Domain Model v1.0 §5 and doc 19 §7)

  1. A fact must trace to at least one evidence row.
  2. A score is never persisted as a current value — always derived or snapshotted.
  3. External API responses are persisted as evidence (90-day minimum retention).
  4. An enrichment run is idempotent within its window (24h default).
  5. Enrichment never silently overwrites human-entered data — surfaces a candidate instead.
  6. Every provider call carries a cost dimension, even if zero.
  7. Every enrichment run creates one timeline event on the company, even if zero facts changed.
26 · Technical Specification

One SPI. Three providers. Additive schema.

Every provider implements the same interface. The framework handles rate limits, retries, timeouts, idempotency, cost, and evidence — so provider code stays small.

The three providers

enrichment/google/
Google Places
Text Search + Place Details. Matching ladder: name+pincode → name+city → name. Fields: place_id, address, phone, website, category, coordinates, business status.
enrichment/website/
Website (Firecrawl)
Fetch page(s), extract deterministic facts only. Emails and phones become candidates, never silent contacts. No AI interpretation in Phase 1.
enrichment/phone/
Phone
Normalize to E.164. Country, region, carrier, type, status, DND. Applied to both company primary and every contact.

The EnrichmentProvider SPI

public interface EnrichmentProvider {
    String key();                                   // "GOOGLE_PLACES", "WEBSITE", "PHONE"
    Set<ProviderCapability> capabilities();

    ProviderResult execute(ProviderRequest request);
    // Providers ONLY implement:
    //   - API call
    //   - Response → structured result (facts + candidates + raw payload)
    // Framework handles: rate-limit, retry, timeout, idempotency, cost,
    //                    evidence recording, timeline event, audit
}

Migrations — additive only

V<next>__enrichment_jobs.sql
CREATE TABLE enrichment_jobs (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  batch_id          UUID,                          -- groups jobs from one Bulk Enrich
  company_id        UUID REFERENCES companies(id) ON DELETE CASCADE,
  contact_id        UUID REFERENCES contacts(id) ON DELETE CASCADE,
  provider_key      VARCHAR(40) NOT NULL,        -- GOOGLE_PLACES | WEBSITE | PHONE
  input_hash        VARCHAR(64) NOT NULL,        -- for idempotency
  status            VARCHAR(20) NOT NULL,        -- QUEUED|RUNNING|SUCCESS|PARTIAL|FAILED
  attempt           SMALLINT NOT NULL DEFAULT 1,
  max_attempts      SMALLINT NOT NULL DEFAULT 3,
  scheduled_at      TIMESTAMPTZ,
  started_at        TIMESTAMPTZ,
  completed_at      TIMESTAMPTZ,
  facts_added       SMALLINT NOT NULL DEFAULT 0,
  facts_updated     SMALLINT NOT NULL DEFAULT 0,
  candidates_added  SMALLINT NOT NULL DEFAULT 0,
  cost_usd          NUMERIC(10,6) NOT NULL DEFAULT 0,
  error_code        VARCHAR(60),
  error_message     TEXT,
  triggered_by      UUID, triggered_via VARCHAR(20) NOT NULL,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK (company_id IS NOT NULL OR contact_id IS NOT NULL)
);

-- Idempotency guard at DB level
CREATE UNIQUE INDEX idx_ej_idempotency
  ON enrichment_jobs(provider_key, input_hash, COALESCE(company_id, contact_id))
  WHERE status IN ('QUEUED', 'RUNNING', 'SUCCESS');

The orchestrator flow

Enrichment request (companyId, providers[]) ↓ For each provider: ├─ Look up provider in ProviderRegistry ├─ Check idempotency (same input+entity within window → cached, cost 0) ├─ Acquire rate-limit slot (defer if hit) ├─ Create enrichment_jobs row status: RUNNING ├─ Call provider.execute(request) with timeout │ On success: ├─ Persist raw payload → evidence (inline JSONB or object-storage) ├─ Apply each FactChange that doesn't overwrite human data ├─ Queue human-review candidates in enrichment_candidates ├─ Record cost ├─ Emit ONE timeline event on the company └─ Update job row status: SUCCESS | PARTIAL On transient failure: ├─ Retry per policy (1s, 4s, 15s) └─ Ultimately status: FAILED_TRANSIENT On permanent failure: └─ No retry status: FAILED_PERMANENT, error recorded

28 · Claude Kickoff Prompt

Two codebases. Twelve constraints.

Unlike prior scopes, Claude inspects both the vyoog-Diagnostic source zip AND the ProspectSoul target repo. Migration map before code.

The twelve critical constraints

  1. Do not recreate companies, contacts, evidence, or any existing table.
  2. Existing research/ AI flow continues to work unchanged. Bridging shim required.
  3. Company Map stays owned-only. Do NOT reintroduce Google/OpenStreetMap/Overpass.
  4. Enrichment is a first-class module. External calls live in enrichment/<provider>/ behind the SPI.
  5. A fact must trace to at least one evidence row.
  6. Enrichment never silently overwrites human-entered data — surfaces candidates.
  7. Extract deterministically only. No AI interpretation in Phase 1.
  8. No silent contact creation from website scraping.
  9. API keys server-side only.
  10. Preserve vyoog-Diagnostic behavior. Deviations require an ADR.
  11. Do not port Phase 2 capabilities.
  12. Every behavior change to existing code requires an ADR.

ADR-on-demand policy

Do not create /adr at project setup

The folder is created only when Claude Code changes existing code, existing flow, or deviates from docs 01–28. First creation adds /adr/README.md with the template.

Expected for Phase 1: ADR-0001 in Track E1 — generalizing research_queue → enrichment_jobs with a bridging shim, actual migration deferred to Phase 1.5.

Also required for: any behavioral deviation from vyoog-Diagnostic when porting a provider.

Definition of done

Do not claim completion until every criterion in doc 27's Release Gate passes, with evidence per criterion. Claude Code reports PASS/FAIL/BLOCKED per criterion per track, plus functional-equivalence results per provider.
