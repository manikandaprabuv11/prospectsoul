Why now — two realities the source file surfaces

Seven of the twelve ICP fields are empty on registry import. A single company routinely carries multiple NIC codes. The maximum observed in one file: 91.

Analysis of the Kanchipuram MSME registry (Kanchipuram_data.xlsx, 123,659 rows) found that 21% of rows carry more than one NIC code, and that phone, website, GST, turnover, and headcount are entirely absent from that source. That's not a flaw in the file — it's registry data, not sales data — but it settles two design questions: NIC must be many-per-company, and completeness scoring must accommodate registry-shaped records.

What this is not

  • Not a change to ICP Qualification (PRD §3.3). NIC filtering is a search facet — no tier, no version, no qualification record.
  • Not an automated scraping engine. The Places lookup is human-triggered, session-scoped, never persisted.
  • Not a second creation path. External results and "+ Add" both route through the existing manual-entry flow — one door in.
  • Not a rewrite of the existing contacts table. ADR-0001 records what changes and why.

Eight new invariants

Extending the numbered invariants in Domain Model v1.0 §5:

  1. NIC classification never blocks company creation.
  2. NIC codes are reference data, not per-record free text.
  3. Every company has zero or one primary NIC. Setting a new primary demotes the previous atomically.
  4. Every company has zero or one primary contact. Same atomic rule.
  5. Contact role is a controlled vocabulary.
  6. External location results are transient — no id, no persistence, until a human explicitly adds one.
  7. Region ≠ State ≠ Cluster ≠ District. Four distinct facets.
  8. Companies List download does not change pipeline state. Only pipeline Export does.

CREATE TABLE company_nic_codes (

Recursive descendant expansion

WITH RECURSIVE subtree AS (
  SELECT id FROM nic_codes WHERE id = :parent
  UNION ALL
  SELECT n.id FROM nic_codes n JOIN subtree s ON n.parent_id = s.id
)
SELECT DISTINCT c.* FROM companies c
JOIN company_nic_codes cnc ON cnc.company_id = c.id
WHERE cnc.nic_code_id IN (SELECT id FROM subtree);

Two verbs — Download vs Export

POST /api/v1/exports

Pipeline Export. State → EXPORTED. Logged in exports. Sales Lead+. Unchanged behavior.

Filter-scoped file. No state change. No exports row. Audit only. Any read role. CSV or XLSX. Optional one-row-per-contact mode.

UX rules — additions

  1. External results are always visually distinct from owned records. Dashed border, different pin style, "not yet in ProspectSoul" label.
  2. A pincode search never writes anything. Only "+ Add" creates a record, always via the manual-entry review form.
  3. NIC is never a required field on any form.
  4. Contact role is required on new contacts. Existing contacts without a role display as "Other".
  5. "Export" and "Download" are distinct words. Not interchangeable in labels, tooltips, or errors.
  6. Quota-exceeded on external search surfaces the problem+json detail verbatim with reset window.
  7. Primary star (★) means "default display" — not "the only one" and not "the correct one".
  8. Grouped-by-NIC view is opt-in. Flat list stays default.
23 · Implementation Plan

Five tracks. Never overlap.

One vertical slice per track. Never start N+1 until N's acceptance criteria all pass, verified against the seed and the Kanchipuram file.

Docs 01–18 slice (already implemented) ↓ release gate passes C1 — NIC Master module ↓ C2 — Company fields + Contact roles + Multi-NIC join ↓ C3 — Hierarchical NIC filter + Grouped view ↓ C4 — Location Intelligence (Google Maps + Places) ↓ C5 — Companies List Download

Track C1 — NIC Master

Goal: Tree exists, admin-editable, imports from master Excel, queryable at any level.

  • Real NIC Excel imports with zero unresolved parents
  • Re-import is idempotent by code
  • Unit tests cover level detection and prefix resolution including skipped-level branches
  • Non-admin gets 403 on all mutations
  • Full-tree endpoint cached in-memory, invalidated on mutation

Track C2 — Company fields + Contact roles + Multi-NIC

Goal: All Sales fields exist; contacts carry roles; multi-NIC works.

  • Existing companies and contacts rows and migrations untouched
  • Kanchipuram Excel: 123,653 created · 6 rejected · 10 flagged · 175,861 NIC join rows
  • is_md_owner=true contacts migrate to role='MD_OWNER', no data loss
  • Primary-flag transitions are atomic (partial unique index enforces at DB)
  • Dedup rule ⓪ on source_reference — zero false candidates on re-import

Track C3 — Hierarchical filter + Grouped view

Goal: Filter by any node and descendants; view results grouped by hierarchy.

  • Recursive descendant expansion — exact counts verified
  • Grouped view returns tree + counts in <500ms for 200-node subtree
  • Lazy-load per group on expand
  • "Directly tagged to parent" bucket appears with correct count

Track C4 — Location Intelligence

Goal: Pincode search shows owned + external, add-to-system routes through manual entry.

  • Places search writes zero rows to any table (integration-asserted)
  • Quota exceeded → 429/422 with clear detail
  • Provider unavailable → 502 — never a silently empty list
  • API key never in frontend bundle; Maps JS key origin-restricted at Google Cloud Console
  • Pincode centroid lookup is offline (seeded reference table)

Track C5 — Companies List Download

Goal: Filter-scoped download, no state change.

  • Does NOT change pipeline state (integration-asserted)
  • Does NOT create an exports row
  • 10k-row CSV streams within 15s
  • UI copy says "Download" — the word "Export" never appears in this modal
24 · Claude Kickoff

Twelve constraints, none negotiable.

Before Claude Code writes a line of code, it reads twelve documents and produces a gap assessment. These are the rules that don't bend.

The twelve constraints

  1. Do not recreate companies or contacts. Additive ALTER TABLE only.
  2. NIC is optional everywhere. Absent → no rows in company_nic_codes. No error.
  3. A company can carry multiple NIC codes and multiple contacts. Scalar-column shortcuts are forbidden. The Kanchipuram file has one row with 91 NIC codes.
  4. Contact role is required on new contacts, from contact_roles. is_md_owner preserved and kept in sync.
  5. Resolve NIC parents by longest existing prefix, not fixed-length truncation. Real data skips levels.
  6. NIC master import must NOT create import_batches rows.
  7. Pincode external search must not fetch from companies. External results are never persisted automatically.
  8. "+ Add" routes through the existing manual-entry endpoint. No second creation path.
  9. Places API key server-side only. Maps JS key separate, origin-restricted.
  10. Do not rename or repurpose "ICP". NIC filtering ≠ ICP Qualification.
  11. "Download" ≠ "Export". Two endpoints, two verbs, one meaning each.
  12. Every behavior change to existing code requires an ADR. New code following specs does not.
Definition of done

Do not claim completion until every criterion in doc 23's Release Gate passes, with evidence per criterion. Claude Code reports PASS/FAIL/BLOCKED per criterion per track, not summary claims.

/adr · Architecture Decision Records

Five decisions worth remembering.

Written the moment they were made, so the next person doesn't have to re-derive them from code six months later.

  • ADR-0001 Contact role becomes a first-class field Free-text designation can't be filtered or reported on. A configured role list can, and existing is_md_owner data migrates cleanly.
  • ADR-0002 Multi-NIC via join table, not scalar column 21% of Kanchipuram rows carry more than one NIC. Max: 91. A scalar column silently loses 90 of them.
  • ADR-0003 Additive company field extension, not table recreation Preserve every existing row and applied migration. Extend, don't replace.
  • ADR-0004 Extended dedup rules for registry sources Registry data has no phone, no website, and repeated proprietor names. Existing rules would generate tens of thousands of false candidates.
  • ADR-0005 Download and Export are distinct operations Overloading the pipeline Export endpoint would silently move companies to EXPORTED on every casual download.
When to write one

Required when you change existing code or behavior, or deviate from docs 01–24. Not required for new code that follows the specs as written.
